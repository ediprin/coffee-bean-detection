# Faruq-v3 ExpertDet HierVIP Screening Protocol

Date frozen: 2026-08-07
Candidate: `HVIP1`
Branch: `agent/expert-hiervip-screening`
Stage: breadth discovery

## Scope

HVIP1 transfers **Hierarchical Visual Instance Promotion (HierVIP)** from
ExpertDet (Zhang et al., 2026), not the full ExpertDet system. VMAM is excluded
because the coffee benchmark does not contain the explicit per-class textual
attribute annotations required by that module.

## Paper operators retained

The implementation follows the retrieved ExpertDet equations:

- Eq. (4): momentum prototype update along every category on an instance's
  hierarchy path;
- Eq. (5): L2 prototype normalization;
- Eq. (6): feature drift `d = 1 - V·f`;
- Eq. (7): adaptive momentum `w = clip(w_base - alpha*d, w_low, w_base)`;
- paper constants: `w_low=0.5`, `w_base=0.8`, `alpha=0.2`;
- Eq. (8): cosine similarity with `tau=0.2`;
- Eq. (9): probability over activated prototypes at the same hierarchy level;
- Eq. (10): weighted hierarchical negative log likelihood;
- `gamma_l = L-l-1`, so the finest level receives the largest weight and the
  root is excluded;
- ExpertDet best HSC loss coefficient `mu=0.001` is frozen for HVIP1.

HierVIP is training-only, consistent with ExpertDet's inference protocol.

## Frozen SNI hierarchy

No validation confusion information may be used. The tree is generated entirely
from `configs/sni21/structured_ontology_v1.yaml`:

`fine_class -> primary_condition -> entity_family -> coffee_quality_sample`

This produces four hierarchy levels. Before training, the runner validates that
`primary_condition` is nested under exactly one `entity_family`, so the mapping
is a tree rather than a many-parent graph.

For the four levels, the fixed ExpertDet weights are `(3, 2, 1, 0)`.

## YOLO26 adaptation boundary

ExpertDet extracts instance features from GT boxes with RRoIAlign. HVIP1 instead
uses embeddings of positively assigned YOLO26 one-to-many P3/P4/P5 locations.
The adaptation is explicit:

- P3/P4/P5 are projected to a shared 128-D space;
- the exact positive assignments generated by native YOLO training provide the
  fine labels;
- every positive embedding updates prototypes on its complete ontology path;
- only activated prototypes participate in HSC;
- one-to-one companion loss remains native YOLO26;
- box regression is untouched;
- the HierVIP projection/prototype tree is not executed at inference.

The 128-D embedding dimension is a project-matched transfer choice for a fair
prototype-family comparison with PCL/APCL; the retrieved ExpertDet method text
does not specify that dimension.

## Frozen training and controls

- seed 42 only for discovery;
- same D0 checkpoint initialization as PCL/APCL;
- primary control: D0FT;
- ACMC1 reported as selected-model reference;
- 50 epochs, imgsz 640, batch 16, workers 2, patience 15;
- optimizer `auto`, close_mosaic 10, max_det 500;
- temperature 0.2;
- HSC loss weight 0.001;
- no post-result hierarchy edits or hyperparameter search.

The 50-epoch project schedule is intentionally matched to the prototype-family
screens; it is not claimed as the original ExpertDet 24-epoch schedule.

## Frozen seed-42 breadth gate

Discovery signal: at least one of:

- Macro mAP50-95 vs D0FT >= +0.20 pp;
- Bottom-3 mAP50-95 vs D0FT >= +0.50 pp;
- Worst-class mAP50-95 vs D0FT >= +0.50 pp.

Safeguards, all required:

- Macro drop vs D0FT no worse than -1.00 pp;
- Bottom-3 drop no worse than -2.00 pp;
- Worst drop no worse than -2.00 pp.

`RETAIN` only keeps HVIP1 in the breadth candidate pool. It does not authorize
holdout access or a claim that full ExpertDet succeeds on coffee.
